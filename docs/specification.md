# Спецификация криптовалютного скринера MetaScalp

Настраиваемые фильтры и расширяемая архитектура

Версия 1.3

19 октября 2026 года

Разработка самостоятельного настольного приложения для поиска торговых пар по заданным условиям ликвидности и активности. Пользователь меняет пороги и состав фильтров, сохраняет профили и получает проверяемое объяснение каждой найденной пары.

| Область | Решение |
| --- | --- |
| Первая биржа | MEXC Spot с котировкой USDT |
| Приложение | Python и PySide6 с Qt Widgets |
| Windows | Client и Companion рядом с MetaScalp |
| macOS | Client arm64 на Mac, Companion и MetaScalp в Parallels |
| Настройки | Профили, атомарное применение и версии правил |
| Расширение | Контракты бирж, источников данных и фильтров |

Спецификация определяет формулы пяти исходных фильтров, точность и полноту данных, протокол интеграции, интерфейс, обработку сбоев и приёмку. Отдельно зафиксированы ограничения источников: неизвестный результат нельзя превращать в подтверждённое соответствие.

Для разработчика предусмотрены контракты модулей, модель данных, пример JSON-профиля и сценарии проверки. Целевые показатели производительности проверяются на воспроизводимом стенде перед выпуском.

## 1 Назначение и результат

Разработать настольный криптовалютный скринер для Windows и macOS. Приложение должно находить торговые пары по настраиваемому набору условий, показывать значения и причины результата, сохранять профили и открывать выбранную пару в MetaScalp. Первой подключаемой биржей является MEXC Spot. Архитектура должна позволять добавлять другие биржи, источники рыночных данных и фильтры без переписывания вычислительного ядра.

Основной сценарий: пользователь задаёт размер своей заявки, выбирает профиль, запускает сканирование и получает список пар, соответствующих включённым условиям. Для каждой строки доступны источник, время проверки, полнота данных и объяснение каждого фильтра. Когда данных недостаточно, приложение показывает неопределённый результат.

Приложение является самостоятельным desktop-клиентом на Python и PySide6 с Qt Widgets. На macOS интерфейс и расчёты выполняются в macOS, а MetaScalp и небольшой агент Companion работают в Windows внутри Parallels. В варианте для Windows оба приложения работают в одной ОС. Qt поддерживает Windows и архитектуру arm64 на macOS; конкретные сборки приложения входят в отдельную матрицу приёмки. [S11, S12]

Слова «должен» и «обязательно» обозначают требования первой версии. «Допускается» означает предусмотренный вариант реализации. Раздел развития описывает отдельные будущие возможности. Числовые параметры производительности ниже являются целями приёмки, а не результатами уже выполненных измерений.

### 1.1 Исходный профиль

### 1.2 Границы первой версии

В первую версию входят полноценный адаптер MEXC Spot, две desktop-сборки, Windows Companion, редактор профилей, пять фильтров, журнал результатов, локальные уведомления, экспорт, диагностика и контракты расширений. Требования к новому адаптеру и новому фильтру проверяются отдельными контрактными тестами.

Размещение и отмена ордеров, автоматическая торговля, расчёт прибыльности стратегии, облачный многопользовательский сервис и загрузка стороннего исполняемого кода через интерфейс находятся за границами этой версии. Кнопка открытия пары изменяет выбранный инструмент в терминале и не совершает сделку.

### 1.3 Явные проектные допущения

Начальный рынок — пары MEXC Spot с валютой котировки USDT. Порог оборота и размер заявки задаются в USDT; рядом с долларовым представлением отображается «≈ USD». Это приближение должно быть видно в интерфейсе и экспорте. Строгий пересчёт в USD требует отдельного источника курса и не должен включаться под видом равенства USDT и USD.

Оборот первой версии использует опубликованный биржей показатель за 24 часа с точностью окна соответствующего источника. Произвольный период оборота, например 6 часов, не появляется в настройках до подключения источника с подтверждённой семантикой такого окна.

MetaScalp устанавливается пользователем отдельно. Его работа в выбранной Windows VM является условием интеграционного испытания. Поддержка SDK и поддержка самого терминала — разные свойства: официальный SDK опубликован под MIT, а приложение скринера не должно представлять весь MetaScalp как открытый код. [S1]

### 1.7 Внутренний прототип

Внутренний прототип проверяет полный путь на 3–5 заранее выбранных парах MEXC Spot USDT: точный снимок MetaScalp, оборот, сделки, публичный API-доступ, все пять фильтров, причины результата и открытие выбранной пары в явно указанной цели терминала. ## 2 Варианты запуска

### 2.1 Windows

Desktop Client содержит интерфейс, вычислительное ядро и собственные адаптеры биржевых API. Companion запускается отдельным пользовательским процессом и подключается к локальному MetaScalp. Связь между Client и Companion работает через loopback. Для обычного запуска приложения не требуются права администратора.

Приложение может запускать принадлежащий ему Companion, контролировать его версию и завершать его при выходе. Процессы MetaScalp и другие экземпляры Companion приложение самовольно не завершает. Для обеих ОС допускается один пишущий Client на каталог данных и файл SQLite, независимо от выбранного профиля. Второй запуск передаёт управление существующему экземпляру либо сообщает, что каталог используется.

### 2.2 macOS и Parallels

Client, ядро, профили и журнал работают в macOS. MetaScalp и Companion находятся в гостевой Windows. Companion устанавливает исходящее соединение с Client по адресу виртуального сетевого интерфейса Mac. После установления соединения обмен командами и данными двусторонний.

Рекомендуемый режим Parallels — Shared Network: он предоставляет гостевой системе доступ к сети через виртуальную подсеть. Адреса и доступность Mac проверяются мастером подключения, без предположения о постоянном IP. [S14]

MetaScalp API доступен внутри Windows через локальные адреса; localhost macOS относится к другой системе. Поэтому Client не должен пытаться обнаружить терминал в VM простым обращением к своему localhost. Взаимодействие с терминалом выполняет Companion. [S2]

### 2.3 Матрица целевой поддержки

| Компонент | Целевая платформа первой версии | Что проверяется перед выпуском |
| --- | --- | --- |
| Desktop Client | Windows 11 x64 | Чистая установка, запуск, UI, сеть, упаковка |
| Desktop Client | macOS на Apple Silicon arm64 | Нативный процесс arm64, запуск, хранение, связь с VM |
| Companion | Windows x64 | SDK, локальные порты, восстановление соединения |
| Companion в Parallels | Сборка x64 в Windows 11 ARM под эмуляцией | Отдельное обязательное испытание фактической совместимости, обмена и паузы VM |

Минимальная версия macOS фиксируется выбранной версией Qt, Python и упаковщика в release manifest. Наличие подходящей архитектуры Qt само по себе не подтверждает совместимость MetaScalp с Windows ARM. Перед выпуском требуется испытание на Mac пользователя либо на сопоставимой конфигурации.

## 3 Настраиваемые фильтры и профили

### 3.1 Модель профиля

Профиль содержит идентификатор, название, описание, номер схемы, ревизию, выбранные привязки источников bindings, параметры каждого фильтра, настройки обновления и отображения. Параметры хранятся в машиночитаемом JSON. Денежные значения и проценты передаются десятичными строками. Версия документа и schema_version профиля являются разными величинами.

Каждый binding имеет уникальный binding_id, биржу, рынок и source_routes — ссылки на конкретные локальные подключения для нужных типов данных. Для режима собственного ключа дополнительно задаются access_profile_ref и account_route_ref. Секреты в профиль не входят. Одного exchange_id недостаточно для выбора между двумя подключениями одной биржи.

Локальная запись подключения разрешает ссылку в provider_id, logical_connection_key при его наличии, network_route_id, credential_ref при необходимости и ревизию записи. Разрешённый набор формирует неизменяемый контекст binding_revision. Смена ссылки в профиле создаёт config_revision; изменение локального маршрута, ключа или сопоставления создаёт новый binding_revision и аннулирует затронутые оценки. Контекст предыдущих событий сохраняется. Маршрут без MetaScalp не обязан иметь его logical_connection_key.

В поставку входит неизменяемый шаблон «Исходные критерии». Пользователь создаёт на его основе рабочий профиль, вводит Q и сохраняет изменения. Поддерживаются создание, копирование, переименование, удаление пользовательского профиля, восстановление значений из шаблона, экспорт и импорт JSON. Профили не содержат секреты и адресные токены сопряжения.

Одновременно активен один профиль сканирования. Несколько профилей можно сохранить и переключать. Одновременное выполнение нескольких профилей относится к развитию продукта, поскольку требует общего бюджета данных и отдельной модели сравнения результатов.

### 3.2 Редактируемые параметры

| Поле | Исходное значение | Допустимые настройки первой версии |
| --- | --- | --- |
| Включение фильтра | Все пять включены | Включён или выключен для каждого фильтра |
| Минимальный оборот | 100000 | Неотрицательное число или отсутствие нижней границы |
| Максимальный оборот | 5000000 | Положительное число или отсутствие верхней границы |
| Минимальный спред | 0.3 процента | Неотрицательное число или отсутствие нижней границы |
| Максимальный спред | 1.5 процента | Положительное число меньше 200 процентов или отсутствие верхней границы |
| Размер заявки Q | Ввод пользователя | Положительная сумма в валюте котировки |
| Зона глубины Bid | 1 процент | Больше 0 и не больше 10 процентов |
| Множитель глубины K | 20 | Положительное десятичное число |
| Минимальное число сделок N | 20 | Сохраняется целое не меньше 1; для включённой активности требуется поддержка источника, у MEXC REST предел 1000 |
| Окно активности W | 300 секунд | Целое от 10 до 3600 секунд |
| Область проверки API | Публичная доступность рынка | Рынок либо рынок и выбранный собственный ключ |

| Набор пар | Все выбранные Spot USDT | Включаемый список и исключения по точным идентификаторам пар |

Структурно некорректный профиль отклоняется целиком. Ограничения N, доступные валюты, рынки и режимы источников определяет адаптер. До применения UI показывает несовместимости по выбранным подключениям. Если ни один выбранный источник не поддерживает параметр включённого фильтра, например N выше доступного лимита, профиль не активируется. Недоступная возможность выключенного фильтра не блокирует остальные условия; его сохранённые значения проходят структурную проверку. Она не включает возможности конкретного подключения: ограничение хвоста адаптера проверяется только для включённой активности. При смешанном наборе источников совместимые продолжают работу, а неподдержанное сочетание биржи и фильтра даёт UNKNOWN/UNSUPPORTED_CAPABILITY. Условие не выключается автоматически.

Диапазоны включают обе числовые границы. Если указаны минимум и максимум, минимум должен быть не больше максимума. Отсутствие обеих границ диапазона допускается только при выключенном соответствующем фильтре. Ноль не обозначает отсутствие границы. Отсутствующая граница кодируется в JSON явным значением null соответствующего поля; пропуск ключа границы, пустая строка и ноль в этой роли недопустимы, и такой профиль отклоняется до активации. Экспорт и импорт сохраняют null без подстановки числа. Профиль должен выбирать непустой universe и хотя бы один разрешённый binding. instance_id обязателен и уникален среди всех фильтров независимо от type_id; type_id также не повторяется в первой версии. Повторяющиеся ключи JSON, идентификаторы фильтров и bindings отклоняются до активации, без поведения «последнее значение побеждает».

### 3.3 Правила применения

Изменения формы сначала сохраняются в черновике. Кнопка «Применить» валидирует весь профиль и атомарно создаёт новую ревизию. Если хотя бы одно поле некорректно, активная ревизия продолжает работать, а ошибка показывается у соответствующего поля.

Каждый результат содержит profile_id и config_revision. Опубликованная ревизия неизменяема. После применения профиль целиком пересчитывается; до этого прежние строки показываются историческими либо со статусом «Пересчитывается». Результат старой ревизии не может заменить строку новой ревизии. Свежие исходные данные допускается повторно использовать, если их состав, источник и полнота соответствуют новым зависимостям. Пересчёт не меняет исходный sample_id, время получения и TTL выборки.

Изменение Q или порога спреда обычно требует только пересчёта. Увеличение зоны стакана или N может потребовать дополнительной загрузки. До её завершения затронутый фильтр получает UNKNOWN с объяснением «Запрашиваются данные для новых параметров».

Включённые фильтры объединяются логическим AND. Произвольные выражения, OR-группы и пользовательский код в редактор не входят. При выключении условия интерфейс показывает «Выключен». Изменение любого порога, окна, зоны или состава условий отмечает профиль как «Свои критерии». Имя профиля, пользовательский Q и настройки отображения сами по себе не меняют исходные условия. Соответствие изменённому профилю не называется соответствием всем исходным пяти условиям.

Проверки корректности входных данных, согласованности источников и свежести обязательны для всех включённых фильтров. Их нельзя выключить вместе с бизнес-фильтром.

### 3.4 Версионирование и импорт

Профиль содержит schema_version и версии определений фильтров. Импорт неизвестного типа фильтра или несовместимой версии создаёт неактивный профиль с описанием несовместимости. Неизвестные поля не должны превращаться в произвольные команды или параметры запроса к терминалу.

Миграция создаёт новую ревизию и сохраняет предыдущую. Экспорт включает единицы измерения, включённые условия, допущение о валюте, область проверки API и настройки свежести. Импорт не запускает сканирование автоматически. Каждый успешный импорт создаёт новый локальный profile_id и начальную ревизию; исходные идентификаторы хранятся только как сведения о происхождении. Существующие опубликованные ревизии и история не изменяются. Импортированные ссылки источников показываются пользователю до активации; неразрешённые ссылки требуют явного сопоставления. Автоматический выбор первого подключения подходящей биржи запрещён.

## 4 Математика и состояния результатов

### 4.1 Общие определения

Единицей отбора является торговая пара на определённой бирже и рынке. Ключ включает exchange_id, market_type, base_asset, quote_asset и venue_symbol. Одноимённые пары на разных биржах считаются разными инструментами. Для данных, связанных с аккаунтом, дополнительно используется идентификатор профиля доступа.

Все цены, количества, обороты, пороги и промежуточные денежные вычисления выполняются десятичной арифметикой. Разрешены только конечные значения с ограниченной длиной и масштабом; NaN и Infinity недействительны. Контекст Decimal выбирается по диапазону адаптера так, чтобы промежуточные операции не меняли пороговое решение. Форматирование и округление для экрана происходят после сравнения. Преобразование исходного JSON сначала во float, а затем в Decimal не удовлетворяет требованию точности.

Основные состояния фильтра: PASS, FAIL, UNKNOWN и DISABLED. Причина состояния является отдельным машинным кодом и понятным текстом. UNKNOWN включает недоступный источник, устаревание, неполноту, ожидание данных и неподдерживаемую возможность. DISABLED означает только выключение пользователем.

### 4.2 Оборот за 24 часа

Оборот V — сумма стоимости исполненных сделок в валюте котировки за окно источника. Для исходного профиля условие задаётся выражением 100000 ≤ V ≤ 5000000. Настройки заменяют границы Vmin и Vmax, сохраняя единицы и период.

Адаптер должен предоставить quote_turnover, валюту, длительность и семантику окна, время получения, а при наличии — границы окна источника. Оборот должен быть конечным неотрицательным десятичным значением. Отрицательный оборот означает UNKNOWN/INVALID_DATA и не сравнивается с пользовательскими границами, в том числе при отсутствии нижнего порога. Значение base_volume × last_price не считается точным оборотом в валюте котировки.

Для MEXC предусмотрен ticker/24hr с quoteVolume. Документация описывает rolling 24h ticker с пометкой «5-minute intervals», но не задаёт точный алгоритм округления границ; в примерах quoteVolume равен null. Числовая пригодность поля, смысл временных полей и допустимая задержка подтверждаются этапом квалификации источника. Пустое или неподтверждённое значение даёт UNKNOWN. Пример ответа в документации не считается измерением реального рынка. [S3]

Если источник перестал предоставлять нужное поле для выбранных пар, адаптер не заменяет его приблизительным вычислением незаметно для пользователя. Подключение резервного поставщика требует подтверждения того же рынка, валюты, периода и полноты. До этого фильтр остаётся UNKNOWN.

### 4.3 Текущий спред

Пусть A — лучшая цена Ask, B — лучшая цена Bid одного снимка. Средняя цена M равна (A + B) / 2. Спред S равен 100 × (A − B) / M. Условие исходного профиля: 0,3 ≤ S ≤ 1,5 процента.

$$
S = 200 \times \frac{A - B}{A + B}
$$

Bid и Ask должны относиться к одной паре, одному источнику, одной сессии и одному снимку. Отрицательные или нулевые цены, отсутствующая сторона и пересечённый стакан A < B означают UNKNOWN. Случай A = B допустим как нулевой спред и проходит только соответствующий настроенный диапазон.

Сравнение можно выполнять без деления: сопоставлять 200 × (A − B) с порогом × (A + B). Это исключает влияние округления частного на границе диапазона. Экран может показывать меньше знаков, чем использует вычисление.

Встроенный показатель Spread MetaScalp не должен автоматически подменять эту формулу: его пользовательская документация связывает расчёт с ценами последних сделок. Для скринера нужен лучший Bid и Ask стакана. [S10]

### 4.4 Глубина Bid относительно размера заявки

Пусть b — ширина зоны в процентах, Q — размер одной заявки в валюте котировки, K — требуемый множитель. Нижняя цена зоны L равна B × (1 − b / 100). Учитываются уровни Bid, удовлетворяющие L ≤ p ≤ B. Для каждого уровня рассчитывается стоимость p × q, где q — количество базового актива. Глубина D равна сумме этих стоимостей.

$$
D \ge K \times Q
$$

Условие: D ≥ K × Q. Исходные значения b = 1 и K = 20. Экран показывает D, требуемое K × Q и отношение D / Q. При полном покрытии D / K разрешено показывать как максимальный размер заявки по этому фильтру на момент снимка. При неполном покрытии D / Q и D / K сохраняют признак нижней оценки: например, «подтверждённый размер не менее 105 USDT», а не точный максимум. Отображаемый допустимый размер не округляется вверх.

Пример: B = 1,000; уровни 1,000 × 800, 0,995 × 800 и 0,990 × 500 дают D = 2091 USDT. Уровень 0,989 не входит в зону 1 процент. При Q = 100 требуется 2000 и фильтр проходит. При Q = 110 требуется 2200 и полный снимок даёт FAIL.

Сумма должна включать все доступные уровни внутри зоны. Её нельзя заменять объёмом лучшего Bid, крупнейшей отдельной заявкой или суммой произвольных первых 20 уровней. Ценовая граница включается точно, до округления для экрана.

Полнота имеет отдельное значение. Если корректный снимок содержит только часть диапазона, видимая сумма является нижней оценкой. При видимой сумме не меньше K × Q положительный результат уже доказан. При меньшей сумме и неподтверждённом покрытии результат UNKNOWN. FAIL допустим только при подтверждённом покрытии всей зоны.

Покрытие можно подтвердить, если источник гарантирует непрерывный снимок от вершины и показанный диапазон доходит до нижней границы либо источник достоверно сообщает исчерпание стороны. Само число возвращённых строк не заменяет такую гарантию. Повторяющиеся ценовые уровни и повреждённые количества обрабатываются по контракту адаптера; неподтверждённые дубликаты не суммируются как дополнительная ликвидность.

### 4.5 Активность в скользящем окне

Окно активности определяется как интервал (T − W, T], где T — время, к которому относится доказательство, по синхронизированной шкале биржи. Для текущего положительного доказательства T является временем оценки. Для отрицательного доказательства используется подтверждённое время среза as_of, указанное в результате отдельно от времени доставки. Сделка ровно на левой границе уже не входит. Исходное условие — не менее N = 20 отдельных исполнений за W = 300 секунд.

Одно исполнение между покупателем и продавцом считается одной сделкой. Нельзя считать сообщения WebSocket, число ценовых изменений или агрегированные группы исполнений. Наличие одинаковых цены, объёма и времени у двух строк само по себе не доказывает дублирование.

Первая MEXC-реализация запрашивает последние N сделок одним ответом recent trades. Ответ поддерживает limit до 1000; пример документации содержит null вместо trade ID. Поэтому список используется как отдельная выборка и не склеивается с предыдущими опросами по ненадёжному ключу. [S4]

Если в одном корректном ответе найдены N отдельных исполнений, однозначно попадающих в текущее окно, условие PASS и экран показывает «≥ N». Точное общее число сделок не утверждается; полнота хвоста для такого положительного доказательства не обязательна. Неопределённость дополнительных строк не отменяет уже достаточное доказательство.

FAIL допустим только на подтверждённый as_of, когда доказанная полнота необходимой части хвоста даёт верхнюю оценку числа сделок в его окне меньше N. Это охватывает и хвост из N записей с N-й записью вне окна, и достоверно полный короткий ответ. Если полнота или неопределённость as_of допускает другой результат, устанавливается UNKNOWN. Время получения HTTP-ответа не становится as_of без гарантии источника. Отрицательное доказательство сохраняет исходный as_of при повторном пересчёте.

Публикуемый контракт MEXC recent trades не содержит отдельного as_of или watermark полноты. Длина массива, сортировка и новый HTTP-запрос не подтверждают эти свойства. До квалификации отрицательного доказательства адаптер объявляет negative_proof_supported=false: достаточные исполнения дают PASS, недостаточные — UNKNOWN. Установить флаг true можно только с зафиксированным основанием полноты и времени среза, а не по наблюдению нескольких похожих ответов. Недопустимый будущий timestamp является ошибкой данных. [S4]

Проверка учитывает погрешность времени. UNKNOWN устанавливается, если неопределённость может изменить пороговый результат. Неопределённость дополнительных исполнений не отменяет PASS, уже доказанный N однозначно входящими исполнениями. Даже без нового сетевого ответа PASS прекращает действовать, когда необходимое для доказательства исполнение выходит из окна. В этом случае результат становится UNKNOWN, а не FAIL: после старой выборки могли произойти новые сделки. Таймер пересчёта не должен ждать следующего опроса.

Потоковый подсчёт в дальнейшем допускается только при гарантии отдельных исполнений, идентификаторов или другого надёжного механизма дедупликации, контроля пропусков и восстановления. До накопления полного окна либо достаточного положительного доказательства потоковый счётчик показывает UNKNOWN.

### 4.6 Разрешение торговли через Spot API

Проверка имеет две области. Режим «Рынок» отвечает, допускает ли биржа API-торговлю этой парой в выбранном направлении. Режим «Мой ключ» дополнительно проверяет выбранный профиль доступа. Область всегда видна в строке результата и в экспорте.

Для MEXC публичная проверка сочетает наличие пары в defaultSymbols и ограничения exchangeInfo. Нормализация учитывает статус 1 как online, isSpotTradingAllowed, разрешение SPOT и tradeSideType: оба направления, только покупка, только продажа либо закрыто. Значения строкового и числового представления приводятся явно. [S5, S6]

Режим собственного ключа требует подтверждения доступа пары через selfSymbols, account.canTrade, действующего ключа и права SPOT_DEAL_WRITE. Для selfSymbols, account и GET apiKeyInfo обязательно право SPOT_ACCOUNT_READ. Его отсутствие делает проверку неполной и даёт UNKNOWN, а не доказательство запрета торговли. [S7, S8, S9]

Все три запроса подписываются выбранным проверяемым ключом. В apiKeyInfo обязательный accessKey равен идентификатору этого ключа; принадлежность ответа сверяется до использования разрешений. Документация называет поле ответа apikey в таблице и accessKey в примере: адаптер поддерживает только проверенные варианты схемы, а при противоречии или неизвестной идентичности возвращает UNKNOWN/INVALID_DATA. Полный ключ не попадает в журнал или экспорт.

permissions разбирается на отдельные токены, а не проверяется поиском подстроки. Для положительного результата требуется status=VALID, торговое разрешение и действующий срок: remainingValidity=-999 означает постоянный ключ, 0 — истёкший, положительное значение — действующий. Неизвестные значения не считаются разрешением. Успешная аутентификация относится к фактически проверенному сетевому маршруту. [S9]

Проверка выполняется для явно выбранного ключа и сетевого маршрута. Отдельный ключ скринера не доказывает права ключа, сохранённого в MetaScalp. На macOS успешный запрос с хоста не доказывает доступность иного маршрута из VM. При несовпадении профиля или маршрута приложение описывает фактически проверенную область.

Режим «Рынок» может работать без ключей. В нём интерфейс пишет «Пара доступна через API; мой ключ не проверен». В режиме «Мой ключ» отсутствие данных о ключе даёт UNKNOWN, явный запрет даёт FAIL. Публичный PASS не повышается автоматически до подтверждения доступа аккаунта.

Статус доступа не гарантирует исполнение конкретной будущей заявки: её цена, количество, остаток средств и изменившиеся биржевые ограничения проверяются отдельно торговой системой. Скринер не отправляет тестовый ордер для проверки прав.

### 4.7 Итог по профилю

| Состояние включённых фильтров | Итог |
| --- | --- |
| Все PASS | Соответствует активному профилю |
| Есть хотя бы один достоверный FAIL | Не соответствует профилю |
| FAIL нет, есть UNKNOWN | Недостаточно данных |
| Все фильтры выключены | Профиль недействителен и не запускается |

Итог строится по полному множеству включённых instance_id опубликованной ревизии, а не только по полученным элементам filter_results. Отсутствующий результат обязательного экземпляра означает UNKNOWN; лишний или дублирующий результат отвергается как ошибка контракта. При независимом достоверном FAIL итог остаётся FAIL. DISABLED не участвует в AND. Не запрошенный из-за раннего отказа фильтр получает UNKNOWN с причиной NOT_EVALUATED; общий результат остаётся FAIL по уже доказанному условию. После истечения срока годности старый FAIL также теряет доказательную силу и пересчитывается.

## 5 Источники данных первой версии

### 5.1 Разделение ответственности

MetaScalp SDK используется как интерфейс к работающему терминалу: обнаружение подключения, получение данных стакана и открытие выбранного инструмента. Собственный адаптер MEXC дополняет его публичными данными о рынке, обороте и отдельных сделках. Такое разделение должно быть скрыто за интерфейсами провайдеров, но происхождение значений доступно в диагностике.

Для подтверждённого спреда и глубины первая версия использует один свежий снимок. REST-снимок MetaScalp выполняет запрос к бирже, поэтому этот путь также потребляет биржевые лимиты. Доступные настройки и возможности проверяются на установленной версии терминала. [S2]

Для исходной реализации используется get_order_book_snapshot выбранного подключения с zoom_index=0; depth_levels и depth_percent не задаются. Процентная зона выделяется локально из исходных уровней. DepthLevels SDK обрезает полученный снимок и не увеличивает лимит биржевого fetch. Группировка цен и преждевременная обрезка диапазона не должны менять сумму или удалять свидетельство покрытия зоны. [S17, S20]

bestBid и bestAsk сверяются с вершинами исходных массивов соответствующей стороны; они не добавляются к bids или asks как дополнительная ликвидность. Пустая сторона, несовместимая вершина и отрицательное количество не дают подтверждённого результата. Параметры реального биржевого fetch, непрерывность уровней от вершины и отсутствие скрытой группировки фиксируются в квалификации источника. Число 5000 в SDK-параметре или стенде само по себе не доказывает такую глубину ответа.

Непроверенное объединение REST-снимка и WebSocket-дельт не входит в путь подтверждённого результата. Узкая движущаяся зона WS сама по себе не подтверждает восстановление уровней, которые вновь вошли в диапазон. Для перехода к такому режиму необходим отдельный контракт последовательности и восстановления.

### 5.2 Карта MEXC

| Потребность | Источник первой версии | Проверка адаптера |
| --- | --- | --- |
| Каталог и правила | exchangeInfo | Тип рынка, валюта, статус, направления, точность |
| Публичная доступность API | defaultSymbols | Полный корректный ответ, время проверки |
| Оборот | ticker/24hr без symbol для всего каталога | Неотрицательный quoteVolume, единицы, семантика окна |

| Активность | trades с limit N | Отдельные исполнения, время, полнота хвоста |
| Время биржи | time | Смещение часов и погрешность |

Нативный MEXC depth документирует цены и количества по уровням и максимальный limit 5000. Большое число уровней не отменяет проверку покрытия требуемой зоны. [S15]

### 5.3 Обязательные проверки совместимости

При подключении Companion сообщает обнаруженную версию MetaScalp, версию SDK, доступные операции и логические подключения. Ядро выбирает явно сохранённое подключение MEXC Spot. Числовой connectionId не считается постоянным идентификатором после перезапуска.

logical_connection_key — устойчивый идентификатор логического подключения терминала. Companion формирует его из полей списка подключений, сохраняющихся после перезапуска терминала: нормализованных exchange_id и market_type и устойчивой метки подключения, заданной пользователем в терминале. Числовой connectionId, позиция в списке, PID и адрес процесса в ключ не входят. Нормализация: нижний регистр для exchange_id и market_type, форма Unicode NFC и обрезка пробелов по краям для метки; части соединяются двоеточием, например mexc:spot:main. Какие поля установленной версии SDK пригодны как устойчивая метка, определяет квалификация SRC-09. Если такого поля нет, Companion показывает наблюдаемые атрибуты подключения, а пользователь назначает псевдоним; псевдоним и наблюдаемые атрибуты сохраняются в локальной записи подключения для повторного распознавания, и псевдоним становится меткой ключа. Два подключения с одинаковым ключом недопустимы: до явного разрешения пользователем операции с этим ключом возвращают CONNECTION_AMBIGUOUS. Изменение метки в терминале создаёт новый ключ; прежняя привязка требует явного сопоставления, кэш и оценки старого ключа не переносятся.

Проверка минимальных возможностей охватывает каталог подключений, получение снимка, точные числовые данные и открытие инструмента. Отсутствие необязательной операции отключает соответствующее действие интерфейса. Отсутствие обязательного источника оставляет зависимый фильтр в UNKNOWN.

SDK фиксируется по версии и commit в сборке. Проверенный commit 51aa2351bd0a38e8d2878a21839fb3743be3bf75 использует стандартные resp.json() и json.loads(raw), без десятичного декодера. Поэтому интеграционный слой обязан декодировать исходный JSON до появления float либо применять закреплённое исправление всех используемых точек декодирования. Преобразование уже полученного float в Decimal не восстанавливает исходную точность. Протокол Companion передаёт точные десятичные значения строками. Подмена SDK-декодера проверяется отдельным сценарием с числом более 16 значащих цифр. [S17, S18]

Прямой резервный источник включается в настройке подключения явно. При его использовании строка показывает смену источника; одна оценка спреда и глубины не смешивает стороны двух поставщиков. Источник выбирается на полный снимок, а не на отдельный уровень.

### 5.4 Однозначное открытие инструмента

Действие instrument.open привязывается к выбранной пользователем цели terminal_target_ref и текущему сопоставлению логического подключения. Стандартный change-ticker задаёт биржу, рынок и тикер, но не конкретный connectionId. При нескольких подходящих подключениях нельзя молча выбирать первое или заменять действие на open_combo. [S2]

Если установленная версия поддерживает адресацию панели, Companion получает актуальный externalId выбранной панели и передаёт ticker и текущий connectionId через PUT /api/ui/documents/{externalId}/ticker. Для цели «Одна панель» разрешён только адресный метод. Общий change-ticker допускается лишь при однозначном подключении и явно выбранной пользователем области активного окна и, при наличии, группы связанных панелей. Он не заменяет действие над одной панелью и не расширяет область действия автоматически. При неоднозначности возвращается CONNECTION_AMBIGUOUS; при закрытой или неподтверждённой цели — TARGET_UNAVAILABLE. Приложение не создаёт произвольные новые окна в обход этого выбора. [S20]

Ответ различает «Команда принята терминалом» и «Переключение подтверждено». Подтверждение требует чтения состояния целевой панели с совпадающими инструментом и подключением в пределах timeout. HTTP-успех асинхронного UI-действия сам по себе не является подтверждением. Если операция чтения состояния недоступна, сообщается только о принятии команды. Повтор после неоднозначного разрыва связи автоматически не выполняется.

### 5.5 Квалификация возможностей источника

Каждое существенное свойство проверяется отдельно для конкретных версии SDK, версии терминала, биржи, операции и сетевого маршрута. Запись квалификации содержит requirement_id из матрицы 19.2, контекст проверки, ожидаемую гарантию, метод, обезличенные исходные данные, результат и ограничения. Проверка одного маршрута не подтверждает другой.

CONFIRMED означает, что нужное свойство подтверждено контрактом источника либо воспроизводимым основанием соответствующей силы. LIMITED означает подтверждённый пригодный режим с явно указанными ограничениями. BLOCKED означает отсутствие основания для обязательного свойства. Повторяемость похожих ответов сама по себе не доказывает полноту, отсутствие будущего исполнения или точный as_of.

До завершения проверки свойство остаётся неподтверждённым; новая редакция спецификации не выставляет capability=true. Для MEXC recent trades отсутствие отрицательного доказательства допустимо как LIMITED при корректном положительном доказательстве. Для отсутствующего точного оборота либо недоказуемого восстановления бюджета обязательного маршрута применяется BLOCKED.

## 6 Архитектура модулей

### 6.1 Компоненты

| Компонент | Ответственность | Чего он не должен знать |
| --- | --- | --- |
| Desktop UI | Таблица, профили, объяснения, действия пользователя | Сырые коды статусов конкретной биржи |
| Application Core | Планирование, сессии, ревизии, итоговые состояния | Детали виджетов и HTTP конкретной биржи |
| Filter Engine | Чистые расчёты по нормализованным данным | Сеть, SDK, ключи, файлы |
| Provider Registry | Выбор подходящего источника по возможностям | UI-раскладка |
| Exchange Adapter | Каталог, данные и ограничения определённой биржи | Правила конкретного пользовательского профиля |

Зависимости направлены от интерфейса и адаптеров к доменным контрактам. Filter Engine не импортирует PySide6, MetaScalp SDK или модуль MEXC. Общий контракт не должен требовать наличия MetaScalp для каждого будущего источника.

### 6.2 Процессы и потоки

Desktop UI работает в главном Qt-потоке. Обычный asyncio-loop в рабочем потоке обслуживает сеть, планировщик и вызовы ядра. Обновления передаются в UI через потокобезопасную очередь и queued signals. Запись в SQLite имеет одного владельца и не блокирует GUI. Это соответствует ограничению Qt на использование QWidget в главном потоке. Обратные команды из UI передаются в asyncio-loop через его потокобезопасный механизм планирования; рабочий поток без Qt event loop не должен ожидать доставку Qt queued slots. Ожидание результата Future не блокирует GUI. [S13]

Companion — отдельный пользовательский процесс с собственным asyncio-loop. Его сбой не завершает Desktop Client. Первой версии не требуются отдельные серверы, message broker, Redis или контейнерная инфраструктура.

Ядро отправляет UI неизменяемые снимки строк пакетами. Число сетевых сообщений не определяет частоту перерисовки. При высокой нагрузке промежуточные UI-обновления одной строки объединяются, а контрольные события сессий и профилей сохраняются.

### 6.3 Контракты данных

Каждая выборка содержит instrument_key, provider_id, binding_id, binding_revision, logical_connection_key при наличии, network_route_id, source_epoch, session_id, sample_id, request_generation, тип данных, параметры покрытия, единицы, время и интервал получения, качество и основание полноты. Аккаунтная выборка дополнительно привязана к access_profile_ref и версии учётных данных без самих секретов. При наличии сохраняются upstream update ID и время события биржи; отсутствие полей обозначается явно.

TradeBatch отдельно содержит as_of либо интервал его неопределённости, tail_complete, основание полноты и погрешность временных меток. Неподтверждённый as_of равен null. BookSnapshot сообщает исходный диапазон и полноту по каждой стороне. Для идентичности строки используется сочетание profile_id, binding_id и instrument_key: разные привязки аккаунтов или источников не сливаются в одну оценку.

Основные доменные модели: Instrument, InstrumentRules, TurnoverSample, BookSnapshot, TradeBatch, ApiAccessSnapshot, ProviderHealth, FilterResult и ScreeningResult. Все модели сериализуются независимо от UI.

FilterResult включает filter_instance_id, filter_type, filter_version, profile_id, config_revision, binding_id, binding_revision, state, reason_code, измеренное значение или нижнюю оценку, порог, единицы, references на использованные sample_id, evaluated_at и время потери годности. Нельзя выдавать нижнюю оценку как точное значение.

ScreeningResult содержит динамическое отображение filter_results по filter_instance_id. Схема результата не ограничена пятью фиксированными полями. Основная таблица имеет постоянные идентификационные колонки и динамические колонки метрик, описанные FilterDefinition. Для нового фильтра всегда доступна универсальная карточка параметров, значений и причины. В первой версии в профиле допускается один экземпляр каждого типа фильтра.

### 6.4 Инварианты контрактов данных

Контракты разделяют структурную проверку и проверку смысла. Структура проверяется до помещения данных в кэш; идентичность, порядок поколений, срок годности и совместимость с профилем проверяются перед использованием. Невалидный результат не заменяет действующую выборку и не создаёт уведомление. Отсутствующий обязательный результат учитывается по правилам раздела 4.7.

| Объект | Обязательные данные | Инвариант |
| --- | --- | --- |
| Выборка | Идентичность и время из 6.3; sample_id и request_generation | sample_id неизменяем. Один идентификатор не обозначает разные данные. Источник и привязка совпадают с разрешённым контекстом. |
| FilterResult | Все поля 6.3; ссылки на выборки; state и reason_code | state принадлежит PASS, FAIL, UNKNOWN, DISABLED. Идентичность экземпляра и версии совпадает с опубликованным профилем. |
| Значение | Единицы, вид оценки, точное значение либо null | Вид: exact, lower_bound или upper_bound. Денежное число — конечная десятичная строка. null не превращается в ноль. |
| Срок годности | evaluated_at; время потери годности; исходные времена | Повторный расчёт не продлевает жизнь выборки. Для UNKNOWN без доказательства срок доказательства равен null. Для DISABLED метрика и ссылки пусты. |
| ScreeningResult | Контекст строки; отображение filter_results по instance_id | Состав сопоставляется со всеми включёнными экземплярами. Дубликаты и посторонние результаты отвергаются. |
| Ошибка расчёта | FILTER_ERROR; безопасное объяснение; контекст | Ошибка одного фильтра даёт UNKNOWN и не завершает независимые расчёты. |

Виды оценок относятся к каждой опубликованной числовой метрике отдельно; состав метрик и порогов задаёт FilterDefinition. Для состояния API-доступа используется нормализованный факт, а не фиктивное числовое значение. Схемы конкретных доменных моделей фиксируются вместе с реализацией по этим инвариантам и проверяются сценариями F, P и R12.

## 7 Расширение бирж и источников

### 7.1 Контракт адаптера биржи

Каждый адаптер реализует описание биржи и возможности, каталог инструментов, нормализацию символов и правил, получение поддерживаемых типов данных, статус соединения, модель лимитов и классификацию ошибок. Вызовы получения данных должны быть отменяемыми, иметь timeout и принимать точный InstrumentKey.

Логические операции контракта: describe_capabilities, list_instruments, get_turnover, get_book_snapshot, get_recent_trades, get_market_access, get_account_access, get_server_time и health. Неподдерживаемая операция возвращает типизированное UnsupportedCapability, а не фиктивный пустой массив.

Провайдер может получать часть данных через MetaScalp и часть напрямую с биржи. Этот выбор задаётся маршрутом данных конкретного подключения. Для каждой операции возвращается provenance — реальный источник и нормализованные характеристики результата.

### 7.2 Возможности адаптера

| Группа | Обязательные характеристики описания |
| --- | --- |
| Рынки | Spot и другие фактически поддержанные рынки, валюты, идентификаторы |
| Оборот | Валюта, период, rolling или календарное окно, точность границ, nullable-поля |
| Стакан | Snapshot или stream, уровни, группировка, покрытие, последовательность, timestamps |
| Сделки | Отдельные или агрегированные, стабильные ID, максимальный хвост, восстановление |
| API-доступ | Публичные и аккаунтные проверки, направления, маршрут проверки |
| Нагрузка | Стоимость операций, scope лимитов, допустимая параллельность, backoff |
| Интеграция с терминалом | Возможность открыть инструмент, идентификатор подключения |

Общие статусы ONLINE, PAUSED, CLOSED и UNKNOWN формируются внутри адаптера. Коды MEXC не должны попадать в универсальные формулы. Аналогично, отсутствие у другой биржи поля isSpotTradingAllowed требует её собственного правила нормализации.

### 7.3 Порядок добавления биржи

Разработчик добавляет пакет адаптера, регистрирует его, реализует нужные возможности и прикладывает обезличенные примеры ответов. Затем выполняются контрактные тесты валют, времени, единиц, полноты стакана, семантики сделок, API-доступа и ошибок. Минимальный интеграционный прогон подтверждает реальные публичные данные.

Добавление второй биржи не требует изменения Filter Engine или основной таблицы UI. Разрешены изменения реестра, пакета адаптера, схемы доступных настроек и тестовых данных. Если новая биржа не поддерживает необходимую метрику, пользователь видит UNKNOWN и конкретное ограничение.

Пары разных бирж показываются отдельными строками. Их оборот и глубина не суммируются автоматически. При одинаковом тикере base и quote также проверяются: совпадение короткого названия монеты не является достаточной идентичностью.

## 8 Расширение набора фильтров

### 8.1 Определение фильтра

FilterDefinition содержит стабильный type_id, версию, название, описание, схему параметров, декларацию входных данных, стандартные метаданные отображения результата, функцию evaluate и функцию объяснения. evaluate получает параметры, нормализованные выборки и неизменяемый EvaluationContext; она возвращает FilterResult без сетевых запросов и побочных эффектов. EvaluationContext содержит время и его погрешность, profile_id, config_revision, binding_id, binding_revision и объявленные фильтром зависимости от order_context. Для глубины это notional_quote и quote_asset, разрешённые для текущего инструмента. Q не читается из UI, глобальной переменной или неописанного внешнего профиля. Специализированный renderer регистрируется отдельно в UI; доменное определение не импортирует Qt.

Схема параметров поддерживает boolean, integer, decimal, enum, диапазон и duration, единицы, минимумы, максимумы, значения по умолчанию и подсказки. По этой схеме UI строит стандартную форму. Специализированный виджет допускается для сложного фильтра, но бизнес-расчёт остаётся независимым от него.

Примеры будущих фильтров: глубина Ask, соотношение Bid и Ask, изменение оборота, волатильность и частота сделок. Эти названия не означают, что расчёты включены в первую поставку. Каждый новый фильтр должен определить формулу, единицы, окно, допустимую точность и поведение при неполных данных.

### 8.2 Зависимости и повторное использование данных

Фильтр объявляет нужные метрики и требования к ним: например, обе стороны одного снимка, непрерывный Bid до заданного процента либо хвост из N отдельных сделок. Планировщик объединяет совместимые запросы и выбирает провайдера с подходящими возможностями.

Одна свежая выборка может обслужить несколько фильтров. Ключ кэша включает инструмент, provider_id, binding_id, binding_revision, logical_connection_key, network_route_id, source_epoch, сессию, тип данных и существенные параметры выборки; для приватных данных также access_profile_ref и версию учётных данных. Все сравнения выполняются по нормализованным точным идентификаторам. Значение от другого ключа или маршрута не подтверждает доступ текущего аккаунта. Изменение ширины диапазона или числа записей не должно выдавать ограниченный старый кэш за расширенные данные.

Взаимные зависимости метрик разрешаются до запуска профиля. Цикл зависимостей или несовместимые единицы отклоняют профиль с понятной ошибкой. Исключение внутри отдельного фильтра превращается в UNKNOWN с кодом FILTER_ERROR и не завершает весь сканер.

Для каждого сочетания инструмента, разрешённого контекста источника и типа данных Core выдаёт возрастающее request_generation независимо от параметров покрытия. Обычно допускается один незавершённый запрос этого сочетания. При повторе после timeout более ранняя операция может ещё выполняться, поэтому проверка поколения обязательна и в этом режиме. После принятия поколения g ответ с меньшим поколением не заменяет выбранную текущую выборку, итог или уведомление. Более старое состояние может оставаться только историческим. Порядок доставки и received_at не определяют новизну исходных данных.

### 8.3 Способ подключения расширений

В первой версии реестры бирж, провайдеров и фильтров формируются из модулей, включённых в сборку. Установка стороннего кода из URL или JSON-профиля не поддерживается. Новая версия расширения поставляется с версией приложения или контролируемого пакета.

Требование расширяемости считается выполненным, когда тестовый дополнительный фильтр и контрактный адаптер регистрируются без изменения существующих формул, структуры ScreeningResult и стандартного редактора параметров. Тестовый адаптер служит проверкой контракта и не объявляется поддержкой второй реальной биржи.

## 9 Протокол между Client и Companion

### 9.1 Соединение и сопряжение

Между процессами используется версионируемый WebSocket-протокол JSON. На одном Windows-компьютере допускается loopback-соединение с одноразово переданным токеном. Между Mac и VM используется TLS с закреплённым сертификатом Client и токеном конкретного Companion.

Client создаёт пакет сопряжения: endpoint, fingerprint сертификата, короткоживущий одноразовый токен и срок действия. Пользователь переносит его в Companion через локальную форму или файл. После успешного обмена токен заменяется отдельным долгоживущим секретом соединения. Пакет и секрет не входят в профиль фильтров.

Сертификат Client самоподписанный и создаётся при первом запуске мастера подключения с ключом ECDSA P-256; закрытый ключ хранится в защищённом хранилище ОС по разделу 15. Исходный срок действия — два года; fingerprint вычисляется как SHA-256 от DER-представления сертификата. Companion принимает только закреплённый fingerprint: сертификат с истёкшим сроком или другим fingerprint отклоняется до рукопожатия протокола, и токен или секрет ему не отправляются. Одноразовый токен действует 10 минут и ровно для одного успешного обмена; долгоживущий секрет не имеет срока, но отзывается в настройках подключения. Ротация сертификата выполняется явно пользователем либо по предупреждению, которое интерфейс показывает за 30 дней до истечения. Ротация создаёт новую пару ключей и новый пакет сопряжения; прежний сертификат остаётся действительным до завершения повторного сопряжения, но не дольше 7 дней и не дольше собственного срока. После истечения или отзыва открытые сессии закрываются с AUTH_REQUIRED, а подключение без повторного сопряжения невозможно. Сроки являются исходными настройками. На loopback без TLS Client передаёт токен запускаемому им Companion через стандартный ввод либо файл с правами только для текущего пользователя, но не через аргументы командной строки и не через переменные окружения; при каждом запуске токен новый. Отдельно запущенный Companion на той же машине сопрягается тем же пакетом, что и Companion в VM.

Слушающий адрес Client ограничивается loopback либо выбранным виртуальным интерфейсом. Приложение не публикует MetaScalp API в Интернет. Изменение адреса, повторное сопряжение, ротация сертификата и отзыв доступа доступны в настройках подключения.

### 9.2 Разрешённые сообщения

| Тип | Назначение |

| hello и welcome | Версия протокола, идентичность процесса, согласование возможностей |
| health и heartbeat | Состояние Companion, терминала и логического подключения |

Имена выше принадлежат протоколу скринера и не являются обещанием одноимённых методов MetaScalp SDK. Gateway выполняет проверенное сопоставление с доступными методами установленной версии.

### 9.3 Конверт сообщения

Обязательные поля после согласования: protocol_version, message_type, session_id, message_id, seq, payload. Hello использует session_id null и seq 0; Client выдаёт новый session_id в welcome. После этого каждая сторона ведёт собственный возрастающий seq, начиная с 1. Ответ содержит request_id. Запрос данных содержит instrument_key, logical_connection_key, profile_id, config_revision, binding_id, binding_revision, source_epoch, request_generation, относительный timeout и параметры выборки. Биржевое чтение дополнительно содержит одноразовый permit_id, limit_scope_id, limit_epoch и зарезервированный вес. Ответ повторяет идентичность запроса и разрешённого источника; при ошибке до отправки явно сообщает not_dispatched. Денежные поля payload представлены строками. Повторное исполнение permit_id запрещено.

source_epoch обозначает поколение наблюдаемого контекста источника. Он меняется после обнаруженного переподключения, изменения сопоставления, потери транспорта к MetaScalp или утраты непрерывности наблюдения. Companion опрашивает локальное состояние используемых подключений каждые 2 секунды; после 6 секунд без достоверного состояния поколение закрывается. Эти локальные опросы не считаются биржевыми чтениями, пока маршрут не доказывает обратное.

SDK не предоставляет подтверждённой гарантии сообщения о каждом кратком внутреннем reconnect биржи. source_epoch не используется как доказательство такой наблюдаемости. Свежесть отдельного REST-снимка проверяется по контракту запроса. Выборки, кэш и возможности привязаны к logical_connection_key и source_epoch; изменение одного подключения не аннулирует независимый источник другой биржи.

Sequence seq обнаруживает пропуск в собственном канале своего направления, но не доказывает отсутствие потерь между биржей и MetaScalp. Для upstream-последовательности используются отдельные поля с собственной подтверждённой семантикой. Сообщение старой сессии отклоняется; неожиданный пропуск или повтор требует восстановления канала. Дедупликация instrument.open по message_id действует в текущей сессии.

Client контролирует окончательный deadline на собственных monotonic-часах и отвергает опоздавший результат; deadline равен моменту отправки плюс переданный timeout и допуск доставки из 11.6. Companion отсчитывает переданный timeout с момента собственного получения и ограничивает им немедленно начатый запрос; ожидающая очередь биржевых чтений находится только в Core. Это локальный бюджет выполнения, а не одинаковый абсолютный deadline на двух машинах. Отмена начавшегося чтения выполняется по возможности; поздний ответ не восстанавливает отменённый контекст.

Граница максимального сообщения по умолчанию — 16 MiB, число одновременных биржевых чтений Companion — 4. Heartbeat, limit.pause, requests.quiesce и ответы на них обрабатываются вне этих слотов и не ждут завершения зависших чтений. Эти значения являются защитными настройками приложения и проверяются на снимках с максимальной глубиной. Превышение возвращает явную ошибку; усечение стакана без признака неполноты запрещено.

### 9.4 Ошибки и повторение

Классы ошибок: AUTH_REQUIRED, PROTOCOL_INCOMPATIBLE, CONNECTION_MISSING, CONNECTION_NOT_READY, CONNECTION_AMBIGUOUS, TARGET_UNAVAILABLE, UNSUPPORTED_CAPABILITY, RATE_LIMITED, BUSY, TIMEOUT, INVALID_DATA, STALE_SESSION, BACKPRESSURE и INTERNAL_ERROR. UI показывает действие для восстановления, а журнал сохраняет request_id и безопасные технические детали.

Запросы чтения можно повторять с новым request_id. instrument.open выполняется не более одного раза на message_id и автоматически не повторяется после неоднозначного разрыва связи. Произвольные URL, HTTP-методы, команды размещения или отмены ордеров через Companion не принимаются.

### 9.5 Структурная и семантическая проверка сообщений

Машиночитаемый базовый контракт находится в docs/contracts/companion-envelope.schema.json; контракт payload ответа requests.quiesced — в docs/contracts/permit-resolution.schema.json. Редакция 1.3 добавляет общие определения common.schema.json и схемы payload hello.schema.json, welcome.schema.json, book-snapshot-request.schema.json, book-snapshot-response.schema.json, instrument-open.schema.json, request-cancel.schema.json, limit-pause.schema.json, requests-quiesce.schema.json и error.schema.json; схема конверта подключает их по message_type, а для парных операций с общим message_type — по наличию request_id. Схема конверта проверяет заголовок и перечисленные payload. health, heartbeat, connections.list, instruments.list, terminal.targets.list и terminal.target.state зависят от полей установленного SDK и получают схемы при реализации соответствующей операции до включения её в capability.

protocol_version равен целому 1. message_id и request_id — непустые идентификаторы не длиннее 128 символов; session_id имеет те же ограничения. hello и welcome используют seq=0; hello имеет session_id=null, welcome содержит выданную сессию и request_id исходного hello. Первый последующий seq равен 1 в каждом направлении. Неизвестные поля конверта и повторяющиеся ключи JSON отклоняются; ограничение 16 MiB применяется до разбора payload.

Ответы book.snapshot.response, limit.paused и requests.quiesced обязательно содержат request_id. Для парных операций без суффикса response ответ сохраняет message_type запроса и добавляет request_id; получатель различает ответ и запрос по этому полю. error, связанный с запросом, также содержит request_id. Структурная проверка не заменяет проверку активной сессии, возрастающего seq и корреляции с реально отправленным запросом.

| Сообщение | Обязательное содержимое payload | Проверка перед действием |
| --- | --- | --- |
| book.snapshot.request | Контекст 9.3, permit_id, limit_scope_id, limit_epoch, вес, timeout и параметры | Точная привязка; действующие поколения; свободный слот; неиспользованный permit_id. |
| book.snapshot.response | Идентичность запроса и источника; снимок либо типизированная ошибка; контекст исполнения | Проверки результата и учёта веса выполняются раздельно; запоздалый снимок не обновляет рынок. not_dispatched=true действует только вместе с объектом resolution по 11.4. |
| limit.pause / limit.paused | limit_scope_id, limit_epoch; для pause — минимальное оставшееся ожидание | Подтверждение относится к той же области и эпохе. Старое подтверждение не возобновляет запросы. |
| requests.quiesce | quiesce_id, limit_scope_id, limit_epoch и точный список permit_id | Область приостановлена; список привязан к журналу Core. Запрос сам по себе не освобождает вес. |
| requests.quiesced | Тот же quiesce_id, область и эпоха; resolutions; unresolved_permit_ids | Каждое разрешение сверяется с журналом и проверяемым доказательством по 11.4. |
| instrument.open | terminal_target_ref, инструмент и разрешённое подключение | Ответ различает accepted и confirmed; confirmed требует проверки состояния цели по 5.4. |
| hello / welcome | hello: идентичность и версия Companion, поддерживаемые версии протокола, auth, платформа, операции, лимиты; welcome: принятые операции, интервалы heartbeat, лимиты, действующие limit_epoch, при сопряжении — секрет соединения | Версия протокола совместима; fingerprint уже проверен транспортом; токен или секрет действителен и использован однократно; payload hello не попадает в журнал и диагностику. |
| request.cancel | target_request_id и permit_id; ответ — исход и при NOT_DISPATCHED объект resolution | Запрос принадлежит текущей сессии; permit_id совпадает с журналом; исход меняет резерв только по правилам 11.4. |

resolutions содержит записи permit_id, origin_session_id, outcome и evidence. Допустимые outcome: NOT_DISPATCHED, COMPLETED, EXECUTION_CONTEXT_CLOSED. evidence указывает evidence_id, observer_id, observed_at, method, source_execution_context_id и artifact_ref. observer_id — идентификатор процесса-наблюдателя: companion_instance_id либо идентификатор запуска Core. observed_at записывается в UTC по RFC 3339 и служит аудиту; интервал удержания Core измеряет на собственных monotonic-часах. artifact_ref состоит из префикса evidence: и локального идентификатора записи в хранилище доказательств наблюдателя; при принятии Core копирует запись в свой журнал. source_execution_context_id — идентификатор контекста исполнения по 11.4; для NOT_DISPATCHED допускается null, для остальных исходов обязателен.

| method | Допустимый outcome | Что должен доказывать наблюдатель |
| --- | --- | --- |
| DISPATCH_BARRIER | NOT_DISPATCHED | Разрешение отмечено как запрещённое в реестре отправителя до любой передачи, путь отправки проверяет реестр атомарно, и ни один исполнитель операцию не получал. Возврат управления локальной задаче или отмена asyncio-задачи этого не доказывают. |
| UPSTREAM_TERMINAL_OUTCOME | COMPLETED | Получен конечный ответ или типизированная ошибка исполнителя именно по этой операции, и её повтор тем же исполнителем исключён. Указывается контекст исполнения, выполнивший операцию. |
| VERIFIED_EXECUTION_CONTEXT_STOP | EXECUTION_CONTEXT_CLOSED | Прекращение исходного контекста исполнения и невозможность доставки старых команд в новый экземпляр проверены по 11.4; идентификатор контекста относится к конкретному запуску процесса. |

Несоответствие method и outcome, чужой контекст исполнения или ссылка на несуществующую запись отклоняются семантической проверкой без изменения резервов.

Один permit_id не может одновременно присутствовать в resolutions и unresolved_permit_ids или повторяться. Доказательство должно соответствовать outcome, исходной сессии и области из журнала. Поля evidence не являются доказательством лишь потому, что прошли JSON Schema. Неполный список сохраняет все неупомянутые резервы. Подтверждение старого permit_id разрешено внутри текущей аутентифицированной сессии как отдельный ответ восстановления; исходное сообщение старой сессии по-прежнему отклоняется.

request.cancel адресует один ранее отправленный запрос чтения: payload содержит target_request_id и его permit_id. Companion отвечает тем же message_type с request_id сообщения отмены и одним из четырёх исходов. NOT_DISPATCHED означает, что чтение не начиналось и больше начаться не может; ответ обязан содержать объект resolution по схеме permit-resolution с методом DISPATCH_BARRIER, и Core обрабатывает его как подтверждение по 11.4, освобождая вес сразу. ALREADY_STARTED означает, что чтение передано исполнителю; отмена выполняется по возможности, вес удерживается, а конечный исход приходит в book.snapshot.response либо устанавливается через requests.quiesce. COMPLETED означает, что ответ уже сформирован и доставлен или будет доставлен. UNKNOWN_REQUEST означает отсутствие записи о запросе в текущей сессии; это не доказательство неотправки, и резерв остаётся до requests.quiesced. Ответ отмены без корректного resolution, с чужим permit_id или с несовпадающим target_request_id отклоняется, и вес сохраняется. Те же правила действуют для resolutions в limit.paused: Companion перечисляет в них только операции, которые не начинались и уже не могут начаться.

## 10 Свежесть и согласованность

### 10.1 Время получения

Для каждого запроса Client записывает собственные monotonic-времена начала и окончания. Если контракт источника гарантирует создание снимка после начала запроса, время от начала запроса до текущей оценки является верхней оценкой возраста снимка. Это учитывает очередь, получение и доставку без вычитания monotonic-часов двух компьютеров.

Для кэшированного ответа время запроса не доказывает свежесть рынка. Отдельно хранятся received_age, возраст подтверждённого состояния source_age и свойство fresh_on_request. При отсутствии timestamp или иной гарантии свежести адаптер не выставляет source_age равным нулю. Успех heartbeat также не обновляет возраст рыночной выборки.

UTC-время используется для отображения и хранения. Для окна сделок ядро оценивает смещение времени биржи через запрос time и сохраняет погрешность, учитывающую задержку. MEXC предоставляет serverTime отдельным endpoint. [S16]

После сна, скачка настенных часов или смены сетевого маршрута старое смещение времени аннулируется. Пограничные временные проверки остаются UNKNOWN до восстановления достаточной точности.

### 10.2 Исходные интервалы

| Тип данных | Целевой интервал запроса | Максимальный возраст для положительного результата |
| --- | --- | --- |
| Каталог и публичные разрешения | 60 секунд | 120 секунд |
| Оборот | 60 секунд | 120 секунд с момента запроса плюс контроль периода источника |
| Стакан активных кандидатов | 5 секунд | 10 секунд |
| Последние N сделок активных кандидатов | 5 секунд | 10 секунд и более раннее истечение доказательства по окну |
| Права собственного ключа | 60 секунд | 120 секунд |
| Синхронизация времени | 30 секунд | 60 секунд |
| Heartbeat Companion | 2 секунды | Разрыв считается обнаруженным после 6 секунд без heartbeat |

Пятиминутная дискретность статистики оборота — свойство источника и показывается отдельно от возраста HTTP-ответа. Если поставщик сообщает достоверные границы окна, проверяется также их допустимая давность; новая загрузка старого ответа не делает статистику актуальной.

Интервалы редактируются в расширенных настройках в пределах возможностей адаптера. Настроенные интервалы и TTL должны быть конечными положительными значениями в пределах схемы адаптера. TTL не может быть меньше настроенного интервала опроса, а TTL активности — больше W. Изменение W, интервала и TTL проверяется атомарно для включённых зависимостей; несовместимый набор не применяется. Увеличение TTL явно меняет допустимый возраст результата и сохраняется в ревизии профиля. Фактический интервал при нехватке лимитов показывается отдельно от желаемого.

### 10.3 Согласованная оценка

Оценка строки использует одну ревизию профиля и набор допустимых свежих выборок. Bid, Ask и глубина берутся из одного снимка; оборот и сделки имеют собственные времена. Снимки разных типов не представляются как одновременный атомарный снимок всей биржи.

При истечении свежести зависимый результат сразу переходит в UNKNOWN, даже если сеть ещё считается подключённой. Последнее значение можно оставить серым с возрастом и причиной. Для активных уведомлений устаревшие значения не используются.

## 11 Планировщик и ограничения нагрузки

### 11.1 Последовательность отбора

Сначала загружается каталог, а затем данные включённых фильтров, пригодных для дешёвой предварительной проверки: публичный API-статус и оборот. Для прошедших включённые предварительные условия загружаются снимки стакана и сделки. После изменения профиля очередь строится заново из актуальных зависимостей.

Выключенное условие не может исключать пару на предварительном этапе. В частности, при выключенном API-фильтре список defaultSymbols не используется как скрытое ограничение каталога, а при выключенном обороте его прежний диапазон не применяется. Независимые границы universe — выбранная биржа, Spot, валюта и явные списки пользователя — сохраняются.

Показатели встроенного скринера могут использоваться как подсказка приоритета только после проверки соответствия. Неэквивалентный Spread, календарный объём или агрегированный счётчик не должны давать окончательный FAIL и исключать подходящую пару из полного обхода.

Непроверенные пары сохраняются в состоянии «Ожидает проверки». Интерфейс показывает число инструментов в каталоге, проверенных на первом этапе, глубоко проверенных, соответствующих профилю и ожидающих очереди. Отсутствие строки среди подтверждённых не означает, что пара была проверена и отвергнута.

### 11.2 Бюджет запросов

Core владеет единым бюджетом своих прямых запросов и инициированных им запросов Companion к той же бирже. Стоимость операций и scope лимита хранятся в версионированной конфигурации адаптера. Для общей NAT-сети консервативно предполагается общий IP-бюджет, пока не доказано иное.

Core хранит единственную ожидающую очередь биржевых чтений. Companion либо начинает разрешённую операцию в свободном слоте после проверки текущих session_id, source_epoch и limit_epoch, либо отвечает BUSY/not_dispatched. Собственной отложенной очереди таких чтений у него нет. Одноразовый permit_id нельзя использовать для повторной попытки.

Core резервирует вес до передачи операции. Для удалённого чтения резерв удерживается до получения завершения, а затем ещё в течение полного окна ограничения на monotonic-часах Client. Подтверждённый not_dispatched позволяет освободить резерв сразу. Timeout, отмена ожидания и разрыв связи не доказывают отсутствия запроса и резерв не возвращают. При неоднозначном исходе резерв сохраняется до requests.quiesced, подтверждающего, что старые операции больше не способны начать биржевой запрос, затем ещё на полное окно. Неопределённость уменьшает доступный бюджет, а не создаёт свободную квоту.

Ответ requests.quiesced перечисляет конкретные permit_id с доказанным завершением или отсутствием отправки и отдельно unresolved_permit_ids. Отмена asyncio-задачи, закрытие HTTP-соединения и перезапуск Companion не подтверждают завершение уже переданного MetaScalp запроса. Если судьба такой операции неизвестна, её резерв сохраняется. Неперечисленные разрешения также остаются неразрешёнными. Запрос requests.quiesce сам по себе ничего не освобождает.

Резервы и блокировки области фиксируются в локальном журнале до отправки операции. После перезапуска Core не забывает неразрешённые permit_id: восстанавливает их, запрашивает подтверждение завершения и отсчитывает необходимое окно заново на новых monotonic-часах. Этот журнал не содержит секретов и не удаляется обычной очисткой истории до разрешения операций.

Тот же общий реестр учитывает прямые запросы; для них локально известен момент отправки. Неизвестная стоимость SDK-метода требует квалификации или обоснованной верхней оценки. Каждый повтор получает отдельное разрешение. Внутренняя нагрузка самого терминала не считается полностью наблюдаемой. Эта консервативная схема может снижать фактическую частоту, но не освобождает вес только из-за задержки ответа.

На дату спецификации MEXC описывает независимые лимиты 300 единиц веса за 10 секунд для IP и 500 за 10 секунд для UID. Область берётся из конкретной операции, а не только из наличия ключа. Начальный рабочий IP-бюджет приложения — 200 единиц за любое скользящее окно 10 секунд; остаток до биржевого лимита резервируется для внешней нагрузки. При обнаруженных ограничениях рабочий бюджет снижается. [S19]

| Операция MEXC | Вес IP в исходной конфигурации |
| --- | --- |
| exchangeInfo | 25 |
| ticker/24hr | 25 |
| depth | 3 |
| trades | 5 |
| defaultSymbols | 1 |
| time | 1 |
| account | 10 |
| selfSymbols | 1 |
| apiKeyInfo | 1 |

Значения фиксируются по документации endpoints. Стоимость MetaScalp snapshot подтверждается отдельно: равенство прямому depth не предполагается без проверки маршрута. Ограничитель окна обязателен независимо от числа параллельных запросов. [S3–S9, S15, S16]

Начальная параллельность глубоких чтений — не более 4. Состав и ёмкость набора регулярно обновляемых пар определяет 11.5; желаемый размер — до 10, фактический размер и частота определяются бюджетом после учёта служебных запросов и фонового обхода. Стенд 10 пар раз в 5 секунд в разделе 17 относится к воспроизведению записи; такая же скорость на живой бирже не гарантируется.

Единица справедливости — допуск одной пары к циклу глубоких запросов, нужных включённым фильтрам. При наличии постоянно непустой фоновой очереди не менее 5 из каждых 20 допусков выделяются ещё не проверенным или дольше всего не проверенным кандидатам; отмена до начала цикла не считается допуском. Это приоритет очереди, а не дополнительная квота поверх биржевого бюджета. Один цикл использует только необходимые операции. При нехватке веса планировщик увеличивает фактический интервал регулярного обновления, сохраняя обход; это видно в UI.

Даже при условной цене снимка 3 и сделок 5 десять регулярно обновляемых пар за 5 секунд расходуют 160 весовых единиц за 10 секунд. Если они должны составлять только 75 процентов полных циклов, глубокая нагрузка вырастает до 213,33 ещё без служебных запросов. Поэтому бюджет 200 нельзя одновременно трактовать как гарантию этой частоты и дополнительного фонового обхода. Реальная стоимость SDK и консервативный резерв могут увеличить задержку. Закрепление не отменяет справедливость и лимиты. Пауза прекращает новые допуски; уже отправленные запросы сохраняют учтённый вес.

### 11.3 Перегрузка и восстановление

При обнаружении 429 или 418 Core прекращает выдавать новые разрешения затронутой области, включая фоновые операции и Companion. limit.pause передаёт limit_scope_id, новое limit_epoch и оставшееся минимальное ожидание; Companion отменяет ещё не начатые операции области и отвечает limit.paused. Более старые разрешения после этого недействительны. При обнаружении ограничения самим Companion он блокирует область локально до отправки ошибки Core. Уже начатый до обнаружения запрос может завершиться и не считается нарушением запрета новых операций.

Минимальное ожидание на стороне Companion отсчитывается после получения сообщения, поэтому сетевой перенос может удлинить паузу, но не сокращает её. Core возобновляет выдачу разрешений после собственного deadline и подтверждения применённого limit_epoch; Companion дополнительно проверяет свой срок. Retry-After задаёт минимум, jitter не может его сократить. При отсутствии заголовка используется консервативная увеличивающаяся задержка. MEXC требует остановки запросов после 429 и описывает Retry-After для 429 и 418. [S19]

Очередь ограничена; отменённые и устаревшие запросы удаляются. Приложение показывает «Ограничение частоты», длительность обхода и число ожидающих пар. Если отдельная очередь контрольных событий переполнена, соединение закрывается с причиной BACKPRESSURE и зависимые результаты аннулируются. Молчаливое удаление события смены сессии или профиля запрещено.

Сохранение прежнего зелёного статуса за пределами TTL ради красивой таблицы запрещено. Снижение частоты не должно выглядеть как продолжающийся мониторинг с прежней скоростью. Ограничения одной биржи не должны останавливать независимый адаптер другой биржи.

### 11.4 Жизненный цикл разрешения и восстановление бюджета

permit_id глобально уникален в журнале Core и никогда не используется повторно. Запись фиксирует область, вес, исходную сессию, limit_epoch и наблюдаемый контекст исполнения. Переход IN_FLIGHT сохраняется до передачи разрешения транспорту. RESERVED означает, что передача ещё не могла начаться; сбой после записи IN_FLIGHT рассматривается как неопределённый исход.

RELEASED — единственное состояние, которое не занимает вес. Состояния HELD и UNRESOLVED переживают перезапуск Core. Для HELD после перезапуска отсчитывается полное окно заново. История результатов не владеет этим журналом и не может его очищать.

| Состояние | Событие и следующий шаг | Условие освобождения веса |
| --- | --- | --- |
| RESERVED | Перед отправкой → IN_FLIGHT; отмена до передачи → RELEASED | Core доказал, что транспорт ещё не получал разрешение. |
| IN_FLIGHT | Конечный исход → HELD; timeout или разрыв → UNRESOLVED | NOT_DISPATCHED с окончательным запретом исполнения → RELEASED. |
| UNRESOLVED | Подтверждённый конечный исход или закрытый контекст → HELD | NOT_DISPATCHED освобождает сразу; любое другое подтверждение требует полного окна. |
| HELD | После полного окна ограничения → RELEASED | Отсчёт начинается при принятии достоверного подтверждения на Core. |
| RELEASED | Конечное состояние; повторные сообщения идемпотентны | Повторное исполнение permit_id запрещено. |

Повтор одного доказательства не создаёт новый резерв, не уменьшает срок удержания и не запускает его заново. Новое поколение соединения, успешный heartbeat, отмена задачи, обычный timeout и перезапуск Companion не доказывают конечный исход. Освобождение по произвольному предельному возрасту запрещено.

Если неразрешённые операции препятствуют следующему необходимому запросу и нет активной обычной паузы rate limit, область получает состояние RECOVERY_REQUIRED. Core останавливает новые биржевые чтения этой области, сохраняя heartbeat и управление. Независимые области продолжают работу. UI показывает занятый вес, число и возраст неразрешённых операций, причину блокировки и действие «Проверить завершение запросов». Рыночные результаты продолжают стареть по TTL.

Восстановление сначала запрещает исполнение старых разрешений во всех участвующих отправителях и выполняет requests.quiesce. Для COMPLETED нужен подтверждённый конечный исход upstream-операции, исключающий её будущие повторы. Для NOT_DISPATCHED нужны отсутствие передачи и окончательный запрет её последующего выполнения. Возврат управления локальной задаче сам по себе этим условиям не соответствует.

Если исход операции восстановить невозможно, допускается EXECUTION_CONTEXT_CLOSED. Проверенный механизм должен доказать прекращение исходного исполнителя MetaScalp и связанных исполнителей, а также невозможность доставки старых команд в новый экземпляр. Идентификатор контекста учитывает конкретный запуск процесса; одного PID, нового source_epoch или изменения connectionId недостаточно. Старые каналы отправки закрываются до подключения нового экземпляра.

Пользователь может штатно завершить терминал и запустить проверку восстановления; скринер не завершает MetaScalp автоматически. Подтверждение пользователя не заменяет наблюдаемое доказательство. После принятия EXECUTION_CONTEXT_CLOSED разрешения переходят в HELD на полное окно. Возобновление требует также окончания Retry-After и согласования действующей limit_epoch.

Если установленная интеграция не позволяет доказать ни конечный исход, ни закрытие контекста, область остаётся RECOVERY_REQUIRED. Диагностика объясняет недоступность безопасного восстановления. Такой обязательный маршрут не проходит SRC-05 и не допускается к публичной версии до выбора проверяемого механизма или квалифицированной альтернативы. Смена маршрута с тем же limit_scope_id не обнуляет его резервы.

### 11.5 Активный набор и ёмкость

Активный набор — пары, которые планировщик обновляет с целевым интервалом быстрых данных: стакана и сделок. Остальные пары, прошедшие предварительный этап, образуют фоновую очередь и обслуживаются по правилу справедливости 11.2 в порядке «дольше всего не проверялась».

Ёмкость активного набора — наибольшее число пар, для которых полный цикл быстрых данных укладывается в бюджет при целевом интервале. Пусть B — рабочий бюджет окна, S — амортизированная стоимость служебных запросов на окно, f — доля фоновой очереди по 11.2 при её непустоте, I — целевой интервал, C — стоимость одного цикла пары, W_d — окно ограничения.

$$
N_{active} = \left\lfloor \frac{(B - S)\,(1 - f)\, I}{C \cdot W_d} \right\rfloor
$$

При B = 200, S около 9, f = 1/4, I = 5 секунд, C = 8 и W_d = 10 секунд ёмкость равна 8 парам; при пустой фоновой очереди — 11; при интервале 15 секунд и TTL 30 секунд — 26. Реальная стоимость снимка SDK подставляется после квалификации SRC-05. Ёмкость пересчитывается при каждом изменении бюджета, стоимости операций, интервала, TTL или состава включённых фильтров и показывается в интерфейсе вместе с текущим заполнением.

Членство определяется в порядке приоритета: закреплённые пользователем пары, затем пары с действующим итогом «Соответствует» в порядке первого подтверждения в текущей ревизии. Пара остаётся в наборе, пока её последний достоверный итог — «Соответствует» и с момента этого итога прошло не более трёх TTL быстрых данных; достоверный FAIL, исключение, снятие закрепления или новая ревизия профиля выводят её из набора. Незанятая ёмкость отдаётся фоновой очереди.

Набор устойчив: при числе подходящих пар сверх ёмкости состав не ротируется автоматически. Избыточные соответствующие пары обслуживаются фоновой долей; после истечения TTL их итог становится UNKNOWN по 10.3 и показывается серым как «Подтверждено ранее» с возрастом, без уведомлений. Интерфейс показывает число соответствующих пар сверх ёмкости и предлагает увеличить интервал и TTL в пределах 10.2, сузить universe или закрепить нужные пары. Если закреплённых пар больше ёмкости, они обновляются по кругу с увеличенным фактическим интервалом, интерфейс предупреждает о превышении, а результаты по-прежнему стареют по TTL.

### 11.6 Исходные значения timeout и backoff

Значения ниже являются исходными настройками приложения. Они редактируются в расширенных настройках в пределах схемы адаптера и проверяются атомарно вместе с интервалами и TTL по 10.2: timeout быстрых запросов не больше их интервала опроса, а сумма timeout и допуска доставки не больше TTL. Истечение timeout само по себе не доказывает исход запроса и не освобождает вес по 11.2.

| Операция | Исходный timeout | Примечание |
| --- | --- | --- |
| Установление TLS, hello и welcome | 5 секунд на каждый шаг | Неудача закрывает соединение и запускает переподключение |
| Прямые публичные запросы каталога, оборота и defaultSymbols | 10 секунд | Большие ответы на весь каталог |
| Прямые запросы стакана, сделок и времени биржи | 4 секунды | Не больше интервала опроса 5 секунд |
| Аккаунтные запросы | 10 секунд | Подписанный маршрут |
| book.snapshot.request | 4 секунды относительного timeout | Deadline Client: отправка + timeout + допуск доставки 1 секунда |
| instrument.open | 5 секунд на принятие и 3 секунды на подтверждение состояния | Подтверждение по 5.4 |
| limit.pause, request.cancel | 2 секунды | Контрольный канал вне слотов чтения |
| requests.quiesce | 10 секунд | Отсутствие ответа оставляет разрешения неразрешёнными |
| Heartbeat | 2 секунды интервал, 6 секунд до разрыва | По 10.2 |

Повтор чтения внутри того же цикла опроса не выполняется: следующая попытка приходит со следующим циклом и отдельным разрешением. Backoff применяется к выдаче новых разрешений затронутой области либо к переподключению; после первого успешного ответа той же операции счётчик сбрасывается.

| Ситуация | Начальная пауза | Рост | Потолок |
| --- | --- | --- | --- |
| 429 или 418 с Retry-After | Значение Retry-After | Без роста | Без потолка |
| 429 или 418 без Retry-After | 10 секунд, полное окно ограничения | Удвоение | 120 секунд |
| Сетевая ошибка или timeout прямого запроса | 1 секунда | Удвоение | 30 секунд |
| Переподключение к Companion | 1 секунда | Удвоение | 30 секунд |
| Ошибка SDK или терминала при живом Companion | 2 секунды | Удвоение | 60 секунд |

К каждой паузе добавляется случайная надбавка до 20 процентов; надбавка никогда не сокращает паузу и не уменьшает Retry-After.

## 12 Состояния приложения и восстановление

Состояния соединения: DISCONNECTED, CONNECTING, AUTHENTICATING, DISCOVERING, READY, DEGRADED и RECONNECTING. Состояния сканирования: STOPPED, STARTING, RUNNING, PAUSED и STOPPING. Состояние пары не подменяется общим состоянием сети.

При старте приложение загружает последний профиль, показывает сохранённые строки как исторические и устанавливает подключения. Актуальный PASS появляется только после проверки необходимых данных. Время прогрева не задаётся фиктивной фиксированной паузой: оно определяется поступлением доказательств.

При разрыве Companion, паузе VM или перезапуске MetaScalp затронутая сессия либо source_epoch закрывается, зависимые результаты становятся UNKNOWN, активные подтверждения аннулируются. После восстановления выполняются новое согласование возможностей, повторное сопоставление логического подключения и получение свежих снимков. Данные старого поколения не оживают автоматически.

Сон Mac обрабатывается явно: после resume либо обнаружения длительной остановки цикла транспортная сессия и прежние подтверждения сбрасываются до обработки накопленных сообщений. Затем выполняются новое согласование и синхронизация времени. Старый сетевой буфер не может вернуть прежний PASS.

Пауза сканирования прекращает новые биржевые запросы и уведомления. Строки продолжают стареть и переходят в UNKNOWN по TTL. При возобновлении планировщик получает актуальные данные в обычном порядке.

Если включён прямой резервный источник, разрыв MetaScalp может оставить часть рыночных расчётов работающей с явной меткой провайдера. Открытие пары в терминале остаётся недоступным до восстановления терминала. В исходном режиме без резервного снимка потеря MetaScalp делает спред и глубину UNKNOWN.

## 13 Пользовательский интерфейс

### 13.1 Первый запуск

Мастер предлагает режим Windows либо macOS с Companion в VM, помогает подключить терминал и выбрать точное логическое соединение. Затем пользователь выбирает шаблон, вводит размер заявки Q, если он нужен включённым фильтрам, и запускает проверку возможностей. При отключении всех зависимых от Q условий его отсутствие не мешает запуску.

Без API-ключа доступен публичный режим. При выборе режима собственного ключа мастер показывает, какой профиль доступа будет проверяться и откуда выполняются запросы. Ввод секретов не является обязательным условием знакомства с интерфейсом и публичного поиска.

### 13.2 Основная таблица

| Колонка | Содержимое |
| --- | --- |
| Биржа и рынок | Например, MEXC Spot |
| Пара | Base, Quote и точный биржевой символ |
| Результат | Соответствует, не соответствует, недостаточно данных |
| Оборот | Значение, валюта, период |
| Спред | Процент по текущему снимку |
| Глубина Bid | Сумма, процент зоны, признак нижней оценки |
| Покрытие заявки | D / Q и требуемый K |
| Активность | Например, ≥ 20 за 5 минут или подтверждённое меньше порога |
| API-доступ | Рынок или мой ключ, разрешённое направление |
| Возраст | Давность критичных данных и последней полной оценки |

Над таблицей находятся профиль и ревизия, Start, Pause, Stop, поиск, итоговый статус источников, прогресс обхода, а также ёмкость и заполнение активного набора по 11.5 с числом соответствующих пар сверх ёмкости. Поддерживаются сортировка, выбор колонок, изменение ширины, закрепление и исключение пары. Исключение меняет черновик профиля и вступает в силу после «Применить». При обновлении сохраняются выделение, прокрутка и начатое пользователем действие.

Фильтры представления: соответствуют профилю, подтверждено ранее, все проверенные, недостаточно данных и ожидают проверки. UI не кодирует состояние только цветом: рядом присутствуют текст и значок. Тема следует системной настройке, с возможностью выбрать светлую или тёмную.

### 13.3 Карточка пары

Карточка показывает все включённые и выключенные условия, текущие параметры, значения, причины, источник и время каждой выборки. Для глубины видны граница диапазона, покрытие и использованные уровни; для активности — режим «достаточно для порога» либо точный счётчик, если такой источник когда-либо подключён.

Действия: открыть в MetaScalp, скопировать символ, закрепить, исключить и экспортировать доказательства текущей оценки. Открытие выполняется только по явному нажатию или горячей клавише с видимой выбранной строкой. Недоступная интеграция объясняется рядом с кнопкой.

### 13.4 Редактор профиля

Каждый фильтр имеет переключатель, название, поля, единицы и короткое объяснение. Для активности доступны пресеты 1, 5 и 15 минут и ручное значение; для остальных параметров — точный числовой ввод. Поддерживаются десятичная точка и запятая при вводе, с однозначной нормализацией.

Форма показывает несохранённые изменения, позволяет отменить их, восстановить шаблон и применить весь набор. Изменение фильтра не должно незаметно запускать дополнительные приватные запросы. Переключение на проверку собственного ключа требует выбора существующего профиля доступа либо его настройки.

### 13.5 Уведомления

Локальные уведомления по умолчанию выключены. После включения они доступны только при переходе в PASS по активному профилю. Повторное уведомление той же пары ограничено интервалом 60 секунд; интервал настраивается. По желанию включаются звук и оповещение о потере связи.

Для подавления одиночного всплеска доступна настройка двух подтверждений; она применяется только к уведомлению. Повторный evaluate того же доказательства не увеличивает счётчик. Второе подтверждение требует нового цикла с новыми sample_id всех включённых быстро обновляемых зависимостей — стакана и сделок. Медленные выборки можно повторно использовать в пределах TTL. Если быстрых зависимостей нет, требуется хотя бы одна новая использованная выборка. Обновление только API-статуса не подтверждает повторно всплеск старого стакана.

Счётчик привязан к инструменту, profile_id/config_revision, binding_id/binding_revision и поколениям источников. Смена контекста или утрата PASS сбрасывает его. Cooldown уведомления учитывает profile_id, binding_id и инструмент и не обнуляется от повторного пересчёта. После новой ревизии профиля уведомление о первоначальном заполнении отключено по умолчанию и включается отдельной настройкой.

Отправка в Telegram, email и другие внешние каналы относится к последующему расширению уведомлений. Первая версия сохраняет события локально.

## 14 Хранение и экспорт

Профили, ревизии, подключения без секретов, журнал переходов и доказательства выбранных оценок хранятся локально в SQLite. Место хранения выбирается через стандартный каталог данных приложения для каждой ОС. Raw-потоки всего рынка постоянно на диск не записываются.

Таблицы логической модели: profiles, profile_revisions, connections, instrument_catalog, screening_events, evidence, permit_journal и limit_scope_journal. Событие содержит снимок параметров либо ссылку на неизменяемую ревизию. Изменение текущего профиля не меняет объяснение старого события.

permit_journal хранит журнал разрешений по 11.4: permit_id, область, вес, исходную сессию, limit_epoch, состояние, моменты переходов и принятые доказательства. limit_scope_journal хранит текущую limit_epoch, срок паузы и признак RECOVERY_REQUIRED каждой области. Обе таблицы ведутся транзакционно вместе с отправкой операций, не содержат секретов и не принадлежат истории результатов. permit_id формируется как UUID версии 4, поэтому его уникальность не зависит от сохранённых записей.

По умолчанию события и доказательства хранятся 7 дней с общим ограничением 1 GiB. Размер имеет приоритет над сроком. Сначала удаляются старые доказательства, затем самые старые события, если это необходимо. Событие с удалёнными подробностями имеет признак unavailable. Очистка не затрагивает профили, текущие настройки и записи permit_journal в состояниях RESERVED, IN_FLIGHT, UNRESOLVED и HELD: такие записи не учитываются в лимите 1 GiB и не удаляются ни по сроку, ни по размеру, ни ручной очисткой истории. Записи RELEASED хранятся 7 дней для идемпотентности повторных подтверждений и затем удаляются. Экспортированные пользователем файлы автоматически не удаляются.

Экспорт CSV содержит текущие строки, состояния всех фильтров, параметры, единицы, область API-проверки, время, источник и признаки нижних оценок. Экспорт JSON профиля содержит только настройки. Экспорт JSON доказательства содержит использованные выборки, точные параметры, безопасный снимок разрешённых привязок, версию фильтра, EvaluationContext и достаточно данных для воспроизводимого пересчёта без ключей. Для аккаунтных проверок экспортируются только нормализованные факты о правах и локальная обезличенная идентичность; полный ответ с балансами, ключом и IP-списком не сохраняется.

При старте после сбоя база проверяется, миграции выполняются транзакционно. Перед изменением схемы создаётся резервная копия. Дамп диагностики исключает секреты, токены, подписи запросов, полные IP-списки и необязательные сведения аккаунта.

## 15 Доступ и безопасные границы интеграции

Секреты сопряжения и необязательные API-ключи хранятся в защищённом хранилище ОС. При недоступности такого хранилища приложение не сохраняет секрет в открытом JSON; допускается режим только на время сессии. Обращения к API используют явно выбранный credential_ref.

Подтверждение чужого ключа через сведения, полученные отдельным read-ключом, не допускается без установленной связи между ними. Скринер не извлекает ключи из внутреннего хранилища MetaScalp и не передаёт их по протоколу Companion.

Все команды Companion проходят allowlist, проверку схемы, точного подключения и инструмента. Терминал может предоставлять более широкий API, чем нужен продукт; Gateway открывает только предусмотренные операции чтения и открытия пары. Ошибки протокола и недействительный токен закрывают соответствующую сессию.

Телеметрия наружу по умолчанию выключена. Экспорт диагностического файла — действие пользователя. Установщик не меняет сетевой режим VM и не открывает произвольные входящие порты без необходимости конкретного выбранного подключения.

## 16 Сборка и сопровождение

В репозитории разделяются доменные контракты, ядро, фильтры, адаптеры, Companion, UI, тесты и документация. Изоляция реализуется границами Python-пакетов и интерфейсов, без обязательного создания большого числа отдельных репозиториев.

Зависимости фиксируются lock-файлом. Release manifest содержит версию приложения, Python, PySide6, SDK, commit адаптеров, версию протокола и схем профилей. Сборки Windows и macOS создаются и проверяются на соответствующих платформах. Python и необходимые зависимости входят в пакет, пользователь не устанавливает их вручную.

Поставляются установочный пакет Windows с Client и Companion, приложение macOS и отдельный пакет Companion для гостевой Windows. Для публичного распространения сборки проходят штатные процедуры подписи платформы; фактическая готовность подписи фиксируется в выпуске. Автоматическое обновление не входит в первую версию.

Документация содержит установку, сопряжение, запуск без ключа, работу с профилями, устранение неисправностей, описание данных и руководство по добавлению адаптера и фильтра. Поставка включает перечень лицензий сторонних зависимостей. Собственный код должен оставаться доступным для сопровождения и расширения; публикация репозитория является отдельным организационным решением.

### 16.1 Ведение спецификации и контрактов

docs/specification.md — основной нормативный текст для разработки. Word-копия содержит те же требования, таблицы, примеры и источники; редакторские комментарии Word, если они есть, служат пояснениями и не содержат требований. Копия редакции 1.3 сформирована из Markdown автоматически; предыдущие копии с комментариями сохраняются как исторические. Исходная версия 1.1 сохраняется как историческая. Изменение требований обновляет Markdown, затронутые схемы и Word-копию одной редакцией; расхождение устраняется до её публикации.

Стабильные идентификаторы F, P и I сохраняются. Для новых требований редакции 1.2 используются SRC-01–SRC-08 и R01–R13; редакция 1.3 добавляет SRC-09, P28, P29, I27–I31, R14 и R15. Матрица 18.5 связывает разделы со сценариями; требование без сценария считается непокрытым и получает сценарий до реализации. В реализации тесты ссылаются на эти идентификаторы; сценарий нельзя считать пройденным только по наличию его описания. Все схемы из docs/contracts проверяются на допустимых и недопустимых примерах из docs/contracts/examples; изменение схемы обновляет примеры той же редакцией. Семантические проверки, которые JSON Schema не выражает, остаются обязательными по 6.4, 9.5 и 11.4.

## 17 Требования к производительности и наблюдаемости

### 17.1 Воспроизводимый профиль испытаний

Базовый стенд обрабатывает каталог из 1500 инструментов, очередь из 100 кандидатов, активное глубокое чтение 10 пар и до 5000 уровней на сторону одного снимка. Числа являются испытательными параметрами и не утверждают фактическое число пар MEXC.

Стенд включает воспроизводимые записи данных и отдельный прогон с живым источником. Для воспроизведения без обращений к бирже фиксируются запись и темп: снимок и пакет сделок каждой из 10 активных пар раз в 5 секунд, таблица до 1500 строк, прогрев 5 минут и измерение 30 минут. В отчёте указываются CPU, RAM, ОС, MetaScalp, VM, её ресурсы, профиль и фактическая частота запросов.

### 17.2 Цели приёмки

| Показатель | Цель |
| --- | --- |
| Реакция основных элементов UI | p95 не более 150 мс от события UI до видимого результата; ожидание сети отдельно |
| Расчёт одной строки после готовности всех входов | p95 не более 50 мс |
| Доставка результата от ядра до таблицы | p95 не более 500 мс до отображения новой ревизии строки |
| Обнаружение потери Companion | Не позже 6 секунд без heartbeat |
| Обозначение устаревания при работающем UI | Не позже 1 секунды после истечения TTL |
| Первые результаты активного набора после готовности источников | Не более двух целевых циклов при свободном бюджете; полный обход отдельно |
| Стабильность | 8 часов без необработанного сбоя и роста неограниченных очередей |
| Завершение приложения | Не более 5 секунд; отмена задач и сохранение принятых записей |

Длительность полного обхода рассчитывается из фактических кандидатов, стоимости запросов и доступного бюджета. Она не заменяется обещанием обновлять все пары с частотой 5 секунд. RAM самого MetaScalp и Windows VM измеряется отдельно от RAM приложения.

Начальные лимиты: кэш рыночных выборок 256 MiB, очередь готовых ответов 32 MiB, очередь контрольных метаданных 256 событий. UI хранит последнюю ожидающую версию каждой строки вместо неограниченного списка изменений. На базовом стенде целевая максимальная RAM Client — 1 GiB, Companion — 512 MiB, без MetaScalp и VM. При исчерпании лимита применяются вытеснение допустимого кэша, backpressure или контролируемое переподключение.

Метрики диагностики: задержка запросов по операции, возраст данных, размер очереди, число активных запросов, потреблённый бюджет, число rate limit, смена сессий, ошибки нормализации, доля UNKNOWN по причинам, длительность полного обхода, ёмкость и заполнение активного набора, число и возраст неразрешённых разрешений.

### 17.3 Практическая пригодность результатов

Прогон квалификации фиксирует набор пар и привязок, профиль, время начала и конца, длительность наблюдения, версии компонентов и фактические интервалы. Выборка включает пары с различающимися оборотом, спредом и активностью; правила выбора записываются до измерений. Отдельно учитываются прогрев, устойчивое наблюдение и восстановление после сбоя.

Отчёт показывает по каждому фильтру и итогу доли PASS, FAIL и UNKNOWN, распределение UNKNOWN по причинам, ожидание первого результата и длительность обхода. Число проверенных пар сопоставляется со всем выбранным universe; ожидающие пары не исключаются из знаменателя без отдельного указания. DISABLED отражается отдельно. Для временных долей задаются период выборки состояния и длительность наблюдения.

Цель этапа — объяснить все наблюдаемые UNKNOWN и проверить, что обязательные метрики вычисляются на контрольных реальных данных. Ожидаемые ограничения, например неподдержанное отрицательное доказательство активности, перечисляются отдельно. Необъяснённая неопределённость и отсутствие обязательного поля блокируют соответствующую возможность. Пригодность наблюдаемой выборки для пользователя фиксируется отдельным решением по отчёту, а не выводится из одного технического PASS.

## 19 Этапы реализации и условия выпуска

Первый этап — подтверждение источников на установленном MetaScalp и реальной MEXC. Проверяются десятичная точность снимка, покрытие диапазона, доступность quoteVolume для нужного рынка, хвост отдельных сделок, публичные ограничения и обмен Mac с VM. Этот этап заканчивается протоколом измерений и обезличенными выборками. Отдельно фиксируются возможности отрицательного доказательства активности, реальный путь и стоимость снимка SDK, наблюдение состояния подключения, устойчивые поля идентичности подключения, точная цель instrument.open и формат сведений о выбранном ключе. До квалификации этих свойств они не объявляются поддержанными. Результаты оформляются по матрице 19.2. После проверки обязательных свойств выполняется внутренний прототип по 19.3; решение о полном объёме дальнейшей разработки принимается по этим двум результатам.

Второй этап — доменные модели, профили, пять чистых фильтров и автоматические проверки формул. Третий — адаптер MEXC, ограниченный Companion, планировщик, время и восстановление сессий. Четвёртый — desktop-интерфейс, журнал, экспорт и уведомления. Пятый — контрактные проверки расширяемости, упаковка и интеграционная приёмка обеих платформ.

Порядок перечисляет зависимости работ и не является оценкой календарных сроков. Детальный план задач формируется по принятой спецификации и результатам первого этапа.

Выпуск первой версии требует прохождения сценариев формул, профилей и интеграции для заявленных платформ, подтверждённой работы всех пяти условий на реальных данных хотя бы для контрольной выборки и отсутствия неклассифицированных подмен источников. Если оборот или точность сделок получить невозможно, соответствующий блок считается незавершённым, а не закрывается приблизительным индикатором.

### 19.1 Риски и предусмотренные решения

| Риск | Предусмотренное поведение или проверка |
| --- | --- |
| MetaScalp или SDK меняет формат | Фиксация версии, capability check, INVALID_DATA при несовместимости |
| MEXC возвращает null в обороте | UNKNOWN; проверка альтернативы с той же семантикой до выпуска |
| Диапазон стакана неполный | Нижняя оценка либо UNKNOWN; FAIL только при полном покрытии |
| Агрегация или пропуски исполнений | Хвост отдельных сделок; отдельная квалификация потокового источника |
| VM засыпает или меняется сеть | Закрытие сессии, старение, переподключение и свежие снимки |
| Растёт число бирж и фильтров | Контракты, capabilities, зависимости и тесты совместимости |
| Лимиты не позволяют желаемую частоту | Справедливый обход, фактическая частота и UNKNOWN после TTL |
| Совместимость Windows ARM отличается от x64 | Отдельный интеграционный прогон и точная матрица поддержки |

### 19.2 Матрица квалификации и условия перехода

Каждая строка имеет отдельную запись CONFIRMED, LIMITED либо BLOCKED по 5.5. В отчёт входят версия и маршрут источника, проверенное свойство, ссылка на обезличенный пример, метод проверки, ограничения и решение. Числа из документации и синтетические фикстуры отмечаются отдельно от измерений реального источника.

| ID | Проверяемое свойство | Условие принятия |
| --- | --- | --- |
| SRC-01 | Десятичная точность SDK и протокола | Исходное число более 16 значащих цифр сохраняется до расчёта; float не появляется на пути декодирования. F20, F23. |
| SRC-02 | Исходные уровни и покрытие стакана | Зафиксированы группировка, вершины и основание покрытия; неполнота видима и обрабатывается по 4.4. F09–F11, F31, I23. |
| SRC-03 | Точный оборот и окно источника | Реальный quoteVolume пригоден для контрольной выборки; валюта, период, null и задержка определены. F01–F03, F24, R03. |
| SRC-04 | Отдельные сделки и временные границы | Положительное доказательство корректно. Отрицательное включается только с основанием as_of и полноты; иначе LIMITED. F12–F16, F22, F27–F29, R02. |
| SRC-05 | Цена запроса и прекращение исполнения | Известна стоимость или обоснованная верхняя оценка; доказуемый путь восстановления UNRESOLVED воспроизведён. I15–I17, I24–I26, R07–R11. |
| SRC-06 | Точная цель instrument.open | Проверены выбранные панель и подключение, неоднозначность и различие accepted / confirmed. I18–I19. |
| SRC-07 | Связь Windows и Mac с VM | На заявленной конфигурации проверены обмен, пауза VM, сон Mac и повторное подключение. I01–I04, I06, I12. |
| SRC-08 | Собственный ключ и маршрут проверки | Проверены идентичность, право чтения и торговые факты без утечки секретов. Для прототипа в режиме «Рынок» отложено; для режима ключа первой версии обязательно. I21–I22. |
| SRC-09 | Устойчивая идентичность логического подключения | Поля списка подключений, сохраняющиеся после перезапуска терминала, определены; при их отсутствии работает псевдоним по 5.3; совпадения ключей выявляются. I04, I18, I27. |

Переход к внутреннему прототипу разрешён после квалификации нужных ему свойств SRC-01–SRC-07 и SRC-09 на выбранной конфигурации. LIMITED допустим только если сохранена семантика соответствующего фильтра и ограничение принято в отчёте. BLOCKED обязательного свойства останавливает этот переход; квалифицированная замена источника требует обновления маршрута, возможностей и повторной проверки затронутых строк.

### 19.3 Критерии завершения внутреннего прототипа

До запуска фиксируются 3–5 контрольных пар, профиль с Q, привязки, версии и длительность прогона. Прототип получает реальные данные для всех пяти фильтров, сохраняет воспроизводимые доказательства выбранных оценок и показывает причины PASS, FAIL и UNKNOWN. Наличие рыночной пары, одновременно подходящей всем исходным порогам, не является обязательным условием успешного технического прогона.

Проверяются точность на границе порога, истечение TTL без нового ответа, запоздалый результат, разрыв и восстановление Companion, сценарий UNRESOLVED и явное открытие выбранной пары. Повреждения и сбои допустимо инъецировать в воспроизводимом стенде; такие проверки маркируются отдельно от живых измерений. Подтверждение свойств внешнего источника одной инъекцией не заменяется.

Выход этапа: отчёт SRC-01–SRC-07 и SRC-09, обезличенные примеры и доказательства, результаты проверок, метрики по 17.3 и решение о продолжении с перечисленными ограничениями. Затем уточняется план этапов 2–5. Объём публичной первой версии из 1.2 и полная приёмка из 18 остаются обязательными; SRC-08 и каждая заявленная платформа подтверждаются до выпуска.
